02 / AUTOMATION · BEGINNER TO INTERMEDIATE

Test automation

Learn where automation helps, how to build stable checks, and how to maintain a suite that gives the team useful feedback.

SELF-PACED5 LESSONSTOOL-AGNOSTIC

What you will learn

  • Choose suitable tests for automation based on repeatability and risk.
  • Separate test data, actions, and assertions so checks are readable.
  • Reduce flaky results with explicit waits and stable selectors.
  • Use failures as diagnostic feedback and maintain the suite over time.

Course lessons

1. Pick the right work to automate

Automate checks that run often, have a clear expected result, and protect important behavior. Repeated regression checks, critical user journeys, and API contracts are common candidates. Keep one-off visual investigations, unclear requirements, and highly subjective evaluation in human hands until expectations become stable. Automation supports testing; it does not replace product judgment.

2. Make checks readable

Each test should explain the scenario and verify an outcome that matters to a user. Keep setup focused, use descriptive names, and avoid hiding many unrelated assertions inside one test. Reuse helpers for repeated actions, but make the test's intent visible without forcing readers to trace a large utility layer.

3. Prefer stable interactions

Use accessible roles, labels, and stable test identifiers instead of fragile selectors tied to layout or generated CSS. Wait for a meaningful state, such as a confirmation appearing, rather than sleeping for an arbitrary number of seconds. Isolate test data where possible and clean up created records so repeated runs do not depend on execution order.

4. Understand failures and flakiness

A failed check can indicate a product defect, a test defect, environment instability, or data collision. Capture useful logs, screenshots, and network details. Reproduce the failure and fix the underlying cause; routinely retrying until green can hide real regressions and teach the team to ignore alerts.

5. Practice: automate a critical journey

Choose a small sign-in or checkout flow. Write down its expected outcome first, then automate the shortest meaningful path and one failure path. Run the checks repeatedly, vary test data, and review whether the failure output explains what went wrong. Add the suite to a continuous integration run after it behaves consistently on a clean environment.

Takeaway

Measure automation by the quality of feedback it gives, not by the number of scripts in the repository.
